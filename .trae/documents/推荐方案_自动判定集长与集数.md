# 推荐方案：分析后自动判定每集时长与集数

## Summary

把「推荐方案」（`SplitMode.RECOMMEND`）从**只自动挑策略**升级为**同时自动决定 D（每集时长）与 N（集数）**。

用户勾选推荐方案后不再需要填任何时长参数。分析阶段拿到候选点后，系统先从**候选点自身的时间分布**估计内容的自然叙事节拍，据此得到节拍锚点 `N_beat`，再在可行集数区间内搜索 N，
对每个 N 用三种策略各解一次，按**跨 N 可比的归一化分数**选出最优的 (N, 策略) 组合，
把 D、N、节拍依据、策略连同完整落选记录一并回填与展示。

三个关键设计：

1. **不硬编码「短剧该多长」** —— 节拍锚点由素材算出来，总时长与内容共同决定（§1.1）。
2. **代价必须跨集数可比** —— 现有 `total_cost` 跨 N 无效，这是技术核心（§1.2）。
3. **L/U 降级为软偏好** —— 不再硬性排除，只影响打分（§1.3）。

## Current State Analysis

  传入**同一个 `derived`**（同一个 D、同一个 L/U、同一个集数区间），最后取 `total_cost` 最小者。
  → 推荐模式当前的自由度**只有策略权重**，D 与 N 完全由用户预先给定。

## Proposed Changes

### 1. 自动判定的三个部件

#### 1.1 节拍锚点 `N_beat`：先验从素材算出来，不写死

不设「短剧就是 60–120 秒」这种常量。改用**候选点自身的时间分布**估计内容的自然节拍 ——
候选点来自对白句末、镜头边界、黑场，它们在时间轴上的疏密就是内容本身的节奏。

```
gaps  = 候选点相邻间隔（含片尾边界构成完整序列）
P(N)  = T / N                                   # N 集对应的节拍周期
rhythm(N) = 落在 [P(N)(1−p), P(N)(1+p)] 内的间隔占比     # p = 节奏容差，默认 0.35
N_beat = argmax_N rhythm(N)，平局取较小的 N
D_beat = T / N_beat
```

- 实现：间隔排序一次，`np.searchsorted` 统计，O(m log m + |区间| · log m)，**微秒级**，
  可以在任何求解之前跑完。
- **完全独立于求解器**：不用 L/U、不用策略权重、不做 DP，只看全部候选点（含未被选中的）。
  这正是它能当「先验」的原因 —— 和 §1.2 的 DP 代价是两个不相干的信息源。
- 总时长参与方式：`T` 决定节拍周期 `P(N)`，`D_beat = T / N_beat` 最终体现为每集秒数。
  同样长度的素材，内容切得碎 → `N_beat` 大；内容段落长 → `N_beat` 小。
- **曲线平坦时**（候选点均匀分布，内容无明显节拍）：`N_beat` 退回一个形态中性值
  （取区间中位），且 `w_beat` 按曲线峰值锐度自动降权 —— 无信号时不让先验指手画脚，
  交给 DP 代价决定，并在日志说明「本片候选点分布均匀，未检出明显节拍，已弱化节拍先验」。

#### 1.2 跨集数可比的归一化分数（技术核心）

代价函数（`solver.py:20-26`）逐边累加：

```
total_cost = Σ_edges [ |时长 − D| / D × w_duration + (1 − 切评分) × w_boundary ]
```

两项都随集数 N 累加，**绝对值变大不代表变差**。直接比不同 N 的 `total_cost` 无效：
15 秒一集能把所有候选点都用上，每集代价极低，纯比适配度会滑向「集数越多越好」的退化解。

```
per_episode_cost = total_cost / N                              # 切点配不配合
beat_penalty(N)  = |ln(N / N_beat)|                           # 偏离内容节拍的程度
range_penalty(N) = 0 若 N 落在用户 L/U 映射的区间内，否则 |ln(N / N_最近端点)|

score = per_episode_cost + w_beat · beat_penalty(N) + w_user · range_penalty(N)
```

- 三项**正交**：单集适配度（DP 给）、内容节拍（素材给）、用户意图（用户给）。
- 对数空间保证「过长 / 过短」等价，且是比例量纲，跨素材可比。
- 权重：`w_beat = 0.6`（主要决定力，随节拍锐度自动降权）、`w_user = 0.25`（辅助）。
  均为**软约束** —— 数据足够好时可以偏离，偏离量逐项写进日志，不做黑箱。
- 判定用 `score`；`per_episode_cost`、`beat_penalty`、`range_penalty` 三项都写进比较记录，
  便于核对是哪一项起了作用。
- 平局：先取集数少的（长集比碎集更接近成片意图），再比 `total_cost`。
- **同一个 N 内部比三种策略时仍照用 `total_cost` 不变** —— 同 N 下它合法，
  本次不碰 `recommend.py` 现有语义。

#### 1.3 L/U 降级为软参考（按你的选择）

L/U 不再硬性排除任何长度，只通过 `range_penalty` 影响打分。映射关系：

```
N_lo_user = ⌈T / U⌉        N_hi_user = ⌊T / L⌋
```

要让「软」真正成立，**求解窗口必须先放宽**，否则被 L/U 排除的长度根本没机会参与求解：

```
solver_L = min(L_user,  D · (1 − solve_tol))
solver_U = max(U_user,  D · (1 + solve_tol))      solve_tol = 0.5
```

即求解窗口取「用户设定」与「D 中心 ±50%」的**并集**（更宽者胜）。用户的 L/U 仍会被
`range_penalty` 拉回，但不再一票否决。

分支：

- **手动上下限模式**：`range_penalty` 按上式生效，`w_user = 0.25`。
- **百分比浮动模式**：`range_penalty` 权重置 0 —— 浮动比例是围绕自动 D 的容差，
  在 D 未定前没有独立信息，套用它只会自我循环。求解窗直接用 `D · (1 ± solve_tol)`。
  用户要表达强约束就切到手动上下限。

推荐模式下 `check_feasibility` 的 `L ≤ D ≤ U` 阻断检查随之跳过（那是模式 A「用户给了 D」的检查）。

### 2. 新增 `app/core/auto_timing.py`

职责单一：**估计节拍 + 在可行集数区间内搜索 N + 返回一个决策**。不碰 GUI、不碰 plan 转换。

```python
@dataclass(frozen=True)
class BeatProfile:
    """内容节拍估计结果。"""
    anchor_episode_count: int          # N_beat
    anchor_duration: Fraction          # D_beat = T / N_beat
    scores: dict[int, float]           # N → rhythm(N)
    sharpness: float                   # 曲线峰值锐度 ∈ [0,1]，用于自动降权
    flat: bool                         # 无明显节拍
    median_gap: Fraction               # 候选点间隔中位数（交叉校验与可解释性）

@dataclass
class TimingCandidate:
    episode_count: int
    target_duration: Fraction
    strategy: str
    ok: bool
    total_cost: float
    per_episode_cost: float
    beat_penalty: float
    range_penalty: float
    score: float
    plan / solution / problems / notes

@dataclass
class TimingDecision:
    chosen: TimingCandidate | None
    candidates: list[TimingCandidate]   # 含落选者，按 score 升序
    beat: BeatProfile
    feasible_range: tuple[int, int]
    probed: int                        # 实际求解次数（预算内）
    state: UnresolvedState              # 复用 NONE / BUDGET_EXHAUSTED / NO_PATH_IN_GRAPH ...
    notes: list[str]
```

主入口 `auto_decide_timing(candidates, media, settings, *, ends_with_question,
budget=40, strategies) -> TimingDecision`。

**2a. 可行 N 区间**（整数集数，避免浮点网格）：

- `N_floor = 2`（1 集不叫分集），`N_ceil = min(⌊T / 10s⌋, 400)`。
- 手动 L/U：区间取**用户区间与节拍邻域的并集**再放宽 —— 因为 L/U 已软化，
  不能拿它当硬边界。实用做法：`N ∈ [max(2, ⌈T/(D·(1+solve_tol))⌉), min(N_ceil, ⌊T/(D·(1−solve_tol))⌋)]`，
  其中 D 取 `D_beat`；再与用户区间求并集，两端都放开。
- 百分比模式：同上但不含用户区间。
- 区间为空 → `MATH_INFEASIBLE` + 可操作诊断。

**2b. 粗到精搜索**（`_build_cost_matrix` 无法跨 N 复用，必须限流）：

- **粗筛**：log(N) 空间取 ≤16 个采样点（去重排序），每点只跑 `duration` 权重
  （集长偏差主导，最适合初筛）。采样点**在 `N_beat` 邻域内加密**（节拍附近约占一半），
  提高命中质量。
- **精筛**：取粗筛 score 最优的 3 个 N，各跑**全部三种策略**。
- 预算 `max_solves = 40`（按你的选择放宽，代价是分析时间更长）。
  实际求解次数写进决策记录与日志。
- 预算耗尽：用已探到的最优解，`state = BUDGET_EXHAUSTED`，
  日志如实说明「已按预算停止搜索」。
- 一个都没探到可行解：返回 `NO_PATH_IN_GRAPH` 或 `MATH_INFEASIBLE`，
  诊断沿用 `_explain_no_path` 风格（「哪一段切不动 + 该把哪个参数改成多少」），
  保证「应用建议」按钮照常可用。

**2c. 胜出者才做方案转换**：搜索阶段直接用 `CandidateGraphSolver` 出 `GraphSolution`，
**只对最终胜出者**调一次现有 `solve_from_candidates()` 拿 `BoundaryPlan`。
不为每个采样点重建 plan —— 那是最贵的一步，且只需要一次。

## Assumptions & Decisions

- **不预设「短剧该多长」**。初稿的 60–120 秒硬编码先验已取消 —— 那是拿未经确认的数字
  冒充智能。节拍锚点每次分析现算，素材变了结论就变。
- **节拍估计独立于求解器**是刻意设计：它只用全部候选点的时间分布（含没被选中的），
  与 DP 代价是两个不相干的信息源，因此才有资格当先验；否则就是同一份数据的自我循环。
- **节拍检不出时降权而非硬套**：内容无明显节奏时先验应当让位，而不是拿一个假的节拍硬压。
- **L/U 是软参考**：不再硬排除，求解窗口放宽到「用户设定 ∪ D 中心 ±50%」，
  让被 L/U 排除的长度仍有机会参与竞争，只在打分上吃亏。百分比浮动模式在自动模式下
  不承载用户意图（围绕未定 D 的容差没有独立信息），需要强约束就切手动。
- **推荐模式不再要求任何时长输入**。D 从「用户输入」降级为「派生结果」。
  这是行为变更：原先「先填时长再推荐」的用法，在推荐模式下改为什么都不填。
- **不引入新求解器**：仍用现有 DP，不做启发式、不做局部搜索。
  粗到精只是限流手段，不改变「给定 N 下取全局最优」这个既有保证。
- **搜索结果可复现**：纯确定性（无随机、无并行），同一素材同一候选集必得同一决策。
- 决策字段写入 `SplitSettings`，随项目快照一起保存 —— 重开项目仍能看到当时判成了什么。

## 实施记录（与初稿的偏离及原因）

实施中推翻了两处设计，都记在这里，因为它们都源于**原稿里一个想当然的假设**。

### 1. 节拍估计从「节奏吻合度曲线」换成「内容单元计数」

初稿的 `rhythm(N)` 是这样定义的：

```
rhythm(N) = 落在 [ (T/N)(1−p), (T/N)(1+p) ] 内的候选点间隔占比
```

**这个量纲对不上。** 候选点是对白句末 / 镜头边界，相邻间隔是 2–10 秒；
而单集长 60–120 秒。拿「句子间隔」去匹配「集长」，无论 N 取多少都匹配不上——
曲线不会有真正的峰，取到的是噪声。

实际改成**内容单元计数**，量纲一致：

```
D_floor = clamp(8 × 候选间隔中位数, 10s, T/2)     # 一集至少装下 8 句
D_beat  = 24 × 候选间隔中位数                       # 软中心：一集装 24 句
N_beat  = round(T / D_beat)
```

「一个内容单元」就是一句台词，所以全部量纲都来自素材。实测：3 秒一句的片子
30 分钟 → 25 集 × 72 秒；12 秒一句的长独白 → 同样时长只切得动 2 集。
这正是「根据内容和总时长自动分析」应有的行为。

### 2. 「节拍检不出就关掉先验」是错的，必须改成「权重浮动但不为零」

初稿写：间隔分布均匀（变异系数低）就判定「无明显节拍」，把 `w_beat` 归零。
实测三次都退化成 **2 集**。原因是一个被忽略的结构性事实：

```
total_cost / N  里的边界项 = (N−1)·p / N
```

**N 越小它越小。** 单集代价天然偏向少集（边界惩罚被摊到更少的集上）。
先验一旦归零，就没有任何东西从另一侧拉住它，最优解必然滑到"能切几集切几集"。

改成：变异系数只用于**调节**权重（`BEAT_WEIGHT → BEAT_WEIGHT × 0.4`），
**只有压根没有候选点（一个间隔都统计不到）才允许为 0**。

同时修掉一个实打实的 bug：`anchor_seconds` 误写成 `24 × floor_seconds` 而不是
`24 × median`，把 24 个单元放大成 192 个——实测会算出 576 秒一集。

### 3. L/U 的权重必须高于节拍先验

`USER_WEIGHT = 1.2` > `BEAT_WEIGHT = 0.6`。两者都在对数空间度量偏离、量纲相同，
所以谁权重大谁说了算。理由：节拍是系统替用户猜的先验，手动上下限是用户亲手填的。
实测把 `USER_WEIGHT` 设成 0.25 时，用户填 170–190 秒会被判成 72 秒——界面在替用户
做决定。
